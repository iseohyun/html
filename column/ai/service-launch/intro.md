# 이 문서의 용도

- 서비스 개시용 AI 체크리스트
  - 정적 웹 앱 하나를 "남들이 쓰는 서비스"로 열기까지 확인할 일을 모은 문서
  - 사람이 하나씩 따라 하는 설명서이기보다, AI 에이전트에게 "이 장 기준으로 점검하고 설정해 줘"라고 맡기는 기준표
- 시행착오에서 나온 내용
  - `iseohyun.com`과 웹 장기, 퀴즈 앱, KoreaEvent 등을 직접 열면서 실제로 막혔던 곳과 고려해야 했던 것을 정리
  - 일반론보다 "실제로 이렇게 했다"는 사례를 우선
- 서비스 개통 순서대로 구성
  - 주소를 갖고 → 검색에 걸리고 → 사용자를 알아보고 → 데이터를 쌓고 → 소통하고 → 앱이 되고 → 운영하는 순서
  - 앞 장을 마쳐야 뒤 장이 가능한 경우가 많음 (예: HTTPS가 있어야 로그인·알림·설치 가능)
- 대상: 보안 전담 인력이 없는 개인·소규모 서비스

# 직접 하지 말고 부탁하기

## 에이전트에게 맡길 수 있는 것

- 강조하고 싶은 점: 오픈소스를 고르든, 체크리스트를 확인하든 직접 하려 하지 말고 부탁하기
- 어지간한 일은 AI 에이전트가 다 함
  - 코드 작성과 수정, 설정 파일(`manifest`, `robots.txt`, `sitemap.xml`, 워크플로)
  - 보안 규칙 작성, 규칙 문법 검사(dry-run), 규칙 시험 코드
  - 오픈소스 조사와 비교, 라이선스 확인, 고지 파일 정리
  - 코드 전수 검사, 이 문서의 장별 점검
  - 저장소 전체에서 사용처 찾기 (예: "이 컬렉션을 쓰는 앱이 아직 있나")
  - CLI 명령 실행: 빌드, 시험, 검색 색인, 배포 준비
  - 문서 정리: README, CHANGELOG 초안, 설정 순서 문서
- 이 문서 자체도 그렇게 만들어짐: 장마다 실제 저장소의 코드를 읽고 사례를 확인하며 작성

## 부탁하는 법

- 목표와 범위를 함께 말하기
  - 예: "2장 기준으로 `xxxx` 저장소의 SEO 기본기를 점검하고 빠진 것을 채워 줘"
  - 예: "4장의 보안 규칙 패턴으로 `firestore.rules`를 점검해 줘. 배포는 하지 말고"
- 이 문서의 장 이름으로 기준을 주기: 에이전트가 같은 기준으로 반복
- 모호한 결정은 에이전트가 묻게 하기: CSS 방식, 버전 관리 방식, 데이터 위치처럼 나중에 바꾸기 어려운 것

## 맡길 때 지킬 것

- 커밋·푸시·배포는 승인제
  - 결과를 보고 확인한 뒤 "커밋해 줘", "배포해 줘"로 진행
  - 보안 규칙·결제·삭제처럼 되돌리기 어려운 일은 특히
- 결과는 사람이 검토
  - AI의 지적도 틀릴 수 있음: "확인됨"과 "추정"을 구분해 달라고 요청
  - "안 쓰는 코드", "아무도 안 쓰는 컬렉션" 같은 주장은 근거(검색 결과)를 함께 받기
- 규칙은 문서로 남기기 (1장 "프로젝트 규칙 문서"): 다음 세션의 에이전트도 같은 규칙을 따름

# 직접 해야 하는 것

## 왜 직접 해야 하나

- 계정과 책임은 본인 것
  - 서비스 가입, 로그인, 2단계 인증
  - 결제 수단 등록, 요금제 변경, 도메인 구매
  - 약관 동의, 심사 요청 (네이버 검수 등)
- 비밀값은 에이전트를 거치지 않게
  - Client Secret, API 키, 봇 토큰을 대화창에 붙여 넣으면 대화 기록·로그에 남을 수 있음
  - 서비스 업체가 제공하는 콘솔·CLI로 직접 입력
    - 예: `firebase functions:secrets:set 이름` (값을 화면에 보이지 않게 입력)
    - 예: GitHub 저장소 **Settings → Secrets and variables → Actions**
    - 예: 값을 화면에 보이지 않게 입력받는 스크립트를 에이전트가 만들고, 실행과 입력은 직접 (`scripts/set-login-secret.ps1`)
  - 에이전트는 "어디에, 어떤 이름으로 넣을지"까지 준비하고 값은 사람이 넣음
- 사람만 할 수 있는 화면 조작
  - 소유 확인 버튼, 도메인 DNS 화면처럼 계정 로그인이 필요한 콘솔
  - 업체가 API를 제공하면 에이전트가 할 수 있지만, 그 API 키 발급은 다시 직접

# 공개 값과 비밀값

- 헷갈리기 쉬운 값들: 화면 코드에 넣어도 되는 것과 절대 안 되는 것

| 공개 값 (화면 코드에 넣어도 됨) | 비밀값 (서버·비밀값 저장소에만) |
| --- | --- |
| Firebase `apiKey`, `firebaseConfig` (3장) | 서비스 계정 키(JSON) |
| 카카오 REST API 키, 네이버 Client ID (3장) | 카카오·네이버 Client Secret (3장) |
| Web3Forms Access Key (5장) | Resend API 키 (5장) |
| 웹 푸시 VAPID 공개 키 (5장) | Telegram 봇 토큰 (5장) |
| reCAPTCHA 사이트 키 (4장) | 공공데이터 API 키 (7장) |
| Cloudflare 통계 토큰, Sentry DSN, GA4 측정 ID (7장) | GitHub 개인 액세스 토큰 |

- 공개 값이 안전한 이유: 그 값으로 할 수 있는 일이 보안 규칙·승인된 도메인·App Check로 제한됨
- 비밀값이 새면: 지워도 이력에 남음, 즉시 폐기·재발급 (1장 "브랜치와 커밋")
