배포: dist를 서버에 올린다

1Vite · 배포와 팁 · 정적 호스팅
배포: dist를 서버에 올린다
  • 정적 파일: dist는 서버에서 실행할 것이 없는 파일 묶음이므로 어떤 웹 서버에든 올릴 수 있음
  • base: 도메인 바로 아래가 아닌 하위 경로에 올릴 때는 설정의 base를 그 경로로 맞춤

첫 번째 슬라이드는 배포입니다. 앞 문서에서 npm run build가 dist 폴더를 만든다는 것까지 보았습니다. 배포는 그 폴더의 내용을 인터넷에서 접근할 수 있는 서버에 올리는 일입니다.

dist에는 서버에서 실행해야 할 프로그램이 없습니다. 파일을 요청받으면 그대로 내주기만 하면 됩니다. 이런 것을 정적 호스팅이라고 합니다. HTML 시작하기에서 HTML 파일을 서버 폴더에 넣어 열었던 것과 같은 방식입니다.

올릴 곳은 여러 가지입니다. GitHub Pages는 저장소만 있으면 무료로 쓸 수 있습니다. Netlify, Vercel, Cloudflare Pages는 저장소를 연결해 두면 푸시할 때마다 빌드와 배포를 대신 해 줍니다.

Firebase Hosting은 명령 한 줄로 올리고, 직접 운영하는 서버가 있다면 웹 서버가 내주는 폴더에 복사하면 됩니다. 어느 쪽이든 하는 일은 같습니다.

한 가지만 주의합니다. GitHub Pages의 기본 주소처럼 사이트가 도메인 바로 아래가 아니라 하위 경로에 놓이면, 설정의 base를 그 경로로 바꿔야 합니다. 바꾸지 않으면 자원을 엉뚱한 주소에서 찾아 빈 화면이 나옵니다.

2026-11-18 · 도메인 연결은 HTML 시작하기 문서의 「도메인 구매」를 참고합니다

첨부 · base 설정

index.html이 자원을 부르는 주소는 /assets/index-a1b2c3.js처럼 슬래시로 시작합니다. 도메인의 맨 위에서부터 찾는다는 뜻입니다.

사이트 주소base자원 주소
https://example.com/'/' (기본값)/assets/index-a1b2c3.js
https://이름.github.io/my-app/'/my-app/'/my-app/assets/index-a1b2c3.js
어느 경로에 놓일지 모름'./'./assets/index-a1b2c3.js (상대 경로)
export default defineConfig({
  base: '/my-app/',
});

코드에서 public의 파일을 가리킬 때도 base를 붙여야 합니다. import.meta.env.BASE_URL이 그 값을 갖고 있습니다.

const icon = import.meta.env.BASE_URL + 'favicon.svg';
첨부 · 예시 — GitHub Pages에 자동 배포
  1. vite.config.js의 base를 '/저장소이름/'으로 설정합니다 (이름.github.io 저장소이거나 자체 도메인을 쓰면 '/').
  2. 저장소의 Settings → Pages → Source를 GitHub Actions로 바꿉니다.
  3. 아래 파일을 .github/workflows/deploy.yml로 저장하고 푸시합니다.
name: Deploy
on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - uses: actions/deploy-pages@v4

main 브랜치에 푸시할 때마다 GitHub의 서버가 빌드해서 올립니다. dist는 저장소에 올리지 않습니다. Git 사용법은 Git 기초 사용법을 참고합니다.

직접 운영하는 서버 (Nginx · IIS)

dist 안의 내용을 웹 서버의 문서 폴더(Nginx는 /usr/share/nginx/html, IIS는 C:\inetpub\wwwroot)에 복사합니다. dist 폴더 자체가 아니라 그 안의 index.html과 assets가 문서 폴더 바로 아래에 오게 합니다. IIS 설치는 HTML 시작하기의 「IIS서버 설치」를 참고합니다.

새로 고치면 404가 나오는 이유

2Vite · 배포와 팁 · SPA 라우팅
새로 고치면 404가 나오는 이유
  • 원인: 화면 전환은 브라우저 안에서 일어났을 뿐, 서버에는 /about이라는 파일이 없음
  • 해결: 서버가 모르는 경로에는 index.html을 내주게 설정하거나, 해시(#) 주소를 사용

두 번째 슬라이드는 배포한 뒤에 가장 자주 만나는 문제입니다. React 같은 단일 페이지 앱은 HTML 문서를 하나만 받고, 그 뒤의 화면 전환은 Javascript가 처리합니다. 라우팅 라이브러리를 쓰면 메뉴를 누를 때 주소창이 /about으로 바뀌지만, 서버에는 아무 요청도 가지 않습니다.

문제는 그 상태에서 새로 고치거나 그 주소를 다른 사람에게 보냈을 때입니다. 브라우저는 서버에 /about을 요청하는데, 서버에는 그런 파일이 없습니다. dist에는 index.html과 assets뿐이기 때문입니다. 개발 서버에서는 Vite가 알아서 처리해 주므로 배포한 뒤에야 드러납니다.

해결 방법은 두 가지입니다. 첫째는 서버가 모르는 경로를 요청받으면 404 대신 index.html을 내주게 설정하는 것입니다. 그러면 앱이 실행되어 주소창의 경로를 읽고 맞는 화면을 그립니다. 호스팅마다 설정 방법이 있고 첨부에 정리했습니다.

둘째는 해시 주소입니다. 주소에서 # 뒤는 서버로 보내지 않는다는 규칙을 이용합니다. 어떤 화면에 있든 서버가 받는 요청은 항상 루트이므로 서버 설정이 필요 없습니다. 지금 보고 있는 이 사이트가 이 방식입니다. 주소창을 보면 index.html 뒤에 #과 문서 경로가 붙어 있습니다.

2026-11-18 · 라우팅을 쓰지 않는 한 화면짜리 앱에는 해당하지 않습니다

첨부 · 참조 — 캐시 설정

배포했는데 방문자에게 옛 화면이 보인다면 캐시 설정을 확인합니다. Vite의 빌드 결과는 두 종류로 나뉩니다.

파일이름알맞은 캐시
assets/*해시가 붙어 내용이 바뀌면 이름도 바뀜길게 (1년, immutable)
index.html항상 같은 이름캐시하지 않음 (no-cache)

index.html만 매번 새로 받으면, 그 안에 적힌 새 해시 이름을 따라 새 자원을 받게 됩니다. 대부분의 정적 호스팅은 이렇게 기본 설정되어 있습니다.

빌드 도구 없이 만든 사이트는 이 일을 직접 합니다. 이 사이트는 script.js?v=20261118v11처럼 주소 뒤에 날짜 기반 버전을 붙여 같은 효과를 냅니다. Vite의 해시는 이것을 자동으로, 파일마다 따로 해 주는 것입니다.

자주 만나는 문제

3Vite · 배포와 팁 · 문제 해결
자주 만나는 문제
  • 개발과 배포의 차이: 개발 서버에서는 되는데 배포하면 안 되는 문제는 대부분 경로(base)와 환경 변수
  • 확인 순서: 브라우저 콘솔의 오류 → 네트워크 탭의 404 → npm run preview로 재현

세 번째 슬라이드는 자주 만나는 문제 네 가지입니다. 첫째, 배포했더니 빈 화면만 나오는 경우입니다. 브라우저 콘솔을 열면 Javascript와 CSS 파일의 404가 찍혀 있습니다. 하위 경로에 올렸는데 base가 기본값 그대로여서 자원을 도메인 맨 위에서 찾은 것입니다.

둘째, 환경 변수가 undefined로 나오는 경우입니다. 이름이 VITE_로 시작하는지 먼저 확인합니다. 이름이 맞는데도 안 나온다면 .env 파일을 고친 뒤 개발 서버를 다시 시작하지 않은 것입니다. 이 파일은 서버가 뜰 때 한 번만 읽습니다.

셋째, API를 호출하면 CORS 오류가 나는 경우입니다. 개발 서버와 API 서버의 포트가 달라 브라우저가 막은 것입니다. 앞 문서의 프록시 설정으로 개발 서버가 요청을 대신 전달하게 합니다.

넷째, 휴대폰으로 화면을 확인하고 싶은데 접속이 안 되는 경우입니다. 개발 서버는 기본적으로 자기 컴퓨터의 요청만 받습니다. --host 옵션을 주면 같은 네트워크의 다른 기기에도 열리고, 접속할 주소가 터미널에 출력됩니다.

여기에 없는 문제를 만나면 순서대로 확인합니다. 브라우저 콘솔의 오류 메시지를 읽고, 네트워크 탭에서 실패한 요청의 주소를 보고, npm run preview로 내 컴퓨터에서 같은 증상이 나는지 재현합니다. 내 컴퓨터에서 재현되면 빌드의 문제이고, 재현되지 않으면 서버 설정의 문제입니다.

첨부 · 배포 전 확인 목록
  1. npm run build가 오류와 경고 없이 끝나는가
  2. npm run preview에서 모든 화면이 열리고, 콘솔에 오류가 없는가
  3. base가 배포할 주소의 경로와 맞는가
  4. .env.production의 값이 운영 서버를 가리키는가. 비밀 값이 VITE_ 변수에 들어 있지 않은가
  5. 라우팅을 쓴다면, 하위 주소에서 새로 고쳐도 열리는가
  6. node_modules와 dist, .env.local이 Git에 올라가 있지 않은가
