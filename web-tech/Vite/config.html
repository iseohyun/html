vite.config.js

1Vite · 설정과 빌드 · 설정 파일
vite.config.js
  • 설정 파일: 프로젝트 루트의 vite.config.js가 설정 객체 하나를 내보냄. 없어도 기본값으로 동작
  • 구성: 변환을 맡는 plugins, 개발 서버의 server, 배포 파일의 build로 나뉨
vite.config.js
import { defineConfig } from 'vite'import react from '@vitejs/plugin-react' export default defineConfig({ plugins: [react()], base: '/', resolve: { alias: { '@': '/src' } }, server: { port: 3000, open: true, }, build: { outDir: 'dist', },})

첫 번째 슬라이드는 설정 파일입니다. Vite의 설정은 프로젝트 루트의 vite.config.js에 적습니다. 이 파일은 설정 객체 하나를 내보내는 Javascript 모듈입니다. 파일이 없어도 기본값으로 동작하므로, 바꾸고 싶은 항목만 적으면 됩니다.

객체를 defineConfig로 감싸는 것은 에디터의 자동 완성을 위해서입니다. 감싸면 어떤 항목을 적을 수 있는지 에디터가 알려 주고, 이름을 잘못 적으면 표시해 줍니다.

가장 중요한 항목은 plugins입니다. Vite 본체는 JSX를 모르고, React 플러그인이 그 변환을 더해 줍니다. Vue나 Svelte를 쓰면 그 플러그인을 넣습니다. React 템플릿으로 만들었다면 이미 들어 있습니다.

base는 사이트가 놓일 주소의 경로입니다. 도메인 바로 아래가 아니라 하위 폴더에 올린다면 여기에 그 폴더 이름을 적습니다. resolve.alias는 import 경로의 별명입니다. 점을 여러 번 찍어 올라가는 상대 경로 대신 @로 시작하는 경로를 쓸 수 있습니다.

나머지 둘은 쓰이는 때가 다릅니다. server는 개발 서버에만, build는 빌드에만 적용됩니다. 포트 번호나 출력 폴더처럼 명령줄 옵션으로 줄 수 있는 값을 여기에 적어 두면 매번 입력하지 않아도 됩니다.

첨부 · 예시 — 프록시로 CORS 피하기

개발 서버는 localhost:5173이고 API 서버는 localhost:8080이면, 브라우저는 출처가 다르다는 이유로 요청을 막습니다(CORS). 개발 서버가 요청을 대신 전달하게 하면 브라우저 입장에서는 같은 출처가 됩니다.

export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      },
    },
  },
});
fetch('/api/users');        // → http://localhost:8080/api/users 로 전달된다

프록시는 개발 서버에만 있습니다. 배포한 뒤에는 API 서버가 CORS를 허용하거나, 웹 서버가 같은 역할을 해 주어야 합니다.

첨부 · 예시 — 경로 별명 
import { fileURLToPath, URL } from 'node:url';

export default defineConfig({
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
});
import Card from '../../../components/Card.jsx';     // 전
import Card from '@/components/Card.jsx';             // 후

슬라이드의 '/src'는 짧게 적은 것이고, 위처럼 절대 경로로 적는 것이 운영체제에 관계없이 안전합니다. 에디터가 별명을 따라가게 하려면 jsconfig.json(또는 tsconfig.json)의 paths에도 같은 내용을 적습니다.

정적 자원과 환경 변수

2Vite · 설정과 빌드 · assets · public · env
정적 자원과 환경 변수
  • 자원: import한 파일은 이름에 해시가 붙어 묶이고, public의 파일은 이름 그대로 복사됨
  • 환경 변수: .env 파일의 VITE_로 시작하는 값만 import.meta.env로 코드에 전달됨
src/App.jsx
// 1) import 한 자원: 주소를 돌려준다import logo from './assets/logo.png'import './App.css' // 2) public 폴더: 루트 경로로 적는다const icon = '/favicon.svg' // 3) 환경 변수: VITE_ 로 시작하는 것만const api = import.meta.env.VITE_API_URLconst isDev = import.meta.env.DEV export default function App() { return <img src={logo} alt="로고" />}

두 번째 슬라이드는 이미지 같은 자원과 환경 변수입니다. HTML에서는 이미지 경로를 src에 직접 적었습니다. Vite 프로젝트에서는 이미지도 import합니다. 가져온 값은 그 파일의 최종 주소가 담긴 문자열이고, 이것을 src에 넣습니다.

이렇게 하는 이유는 빌드 결과에 있습니다. import한 파일은 이름 뒤에 내용의 해시가 붙어 나갑니다. 파일 내용이 바뀌면 이름이 바뀌므로 브라우저가 옛 파일을 캐시에서 꺼내 쓰는 일이 없습니다. CSS도 같은 방식으로 import합니다.

public 폴더의 파일은 아무 처리 없이 이름 그대로 복사됩니다. 코드에서는 슬래시로 시작하는 경로를 문자열로 적습니다. favicon이나 robots.txt처럼 이름이 바뀌면 안 되는 파일만 여기에 둡니다.

환경 변수는 개발할 때와 배포할 때 달라지는 값을 코드 밖에 두는 방법입니다. 프로젝트 루트의 .env 파일에 적고, 코드에서는 import.meta.env로 읽습니다. DEV처럼 Vite가 미리 넣어 주는 값도 있습니다.

주의할 점은 VITE_로 시작하는 변수만 코드에 전달되고, 전달된 값은 빌드 결과에 글자 그대로 박힌다는 것입니다. 브라우저로 내려가는 파일에 들어가므로 누구나 볼 수 있습니다. 비밀번호나 비밀 키는 넣지 않습니다.

2026-11-18 · .env 파일을 고치면 개발 서버를 다시 시작해야 반영됩니다

첨부 · .env 파일
.env
VITE_API_URL=https://api.example.com
VITE_APP_TITLE=내 앱
DB_PASSWORD=1234            # VITE_ 가 없으므로 코드에 전달되지 않는다
파일읽히는 때
.env항상
.env.local항상. Git에 올리지 않는 개인 설정
.env.developmentnpm run dev일 때
.env.productionnpm run build일 때

뒤에 적힌 파일이 앞의 것을 덮어씁니다. Vite가 미리 넣어 주는 값은 다음과 같습니다.

변수값
import.meta.env.MODE'development' 또는 'production'
import.meta.env.DEV / PROD개발 서버이면 DEV가 true, 빌드이면 PROD가 true
import.meta.env.BASE_URL설정의 base 값

값은 모두 문자열입니다. VITE_DEBUG=false는 문자열 'false'이므로 조건문에서 참이 됩니다. === 'true'로 비교합니다.

빌드: 소스가 배포 파일이 되기까지

3Vite · 설정과 빌드 · vite build
빌드: 소스가 배포 파일이 되기까지
  • 과정: 변환 → 묶기 → 덜어 내기 → 압축 → 해시 붙이기를 거쳐 dist 폴더에 출력
  • 결과: dist는 HTML · CSS · Javascript뿐인 정적 파일. 이 폴더만 서버에 올리면 됨

세 번째 슬라이드는 빌드입니다. 개발 서버는 요청받은 파일을 그때그때 변환했습니다. 실제 서비스에 그 방식을 쓰면 방문자가 수백 개의 작은 파일을 따로 받아야 합니다. 그래서 배포할 때는 npm run build로 전부를 한 번에 처리해 둡니다.

과정은 다섯 단계로 볼 수 있습니다. 먼저 JSX와 TypeScript를 Javascript로 변환합니다. 다음으로 import로 이어진 모듈을 따라가며 몇 개의 파일로 묶습니다. 파일 수가 줄어 방문자의 요청 횟수가 줄어듭니다.

셋째, 가져오기만 하고 쓰지 않은 코드를 덜어 냅니다. 나무를 흔들어 죽은 잎을 떨어뜨린다는 뜻으로 트리 셰이킹이라고 부릅니다. 넷째, 공백과 주석을 지우고 변수 이름을 짧게 바꿔 크기를 줄입니다.

다섯째, 파일 이름에 내용으로 계산한 해시를 붙입니다. 내용이 한 글자라도 바뀌면 이름이 달라지므로, 브라우저의 캐시를 길게 잡아 두어도 새 버전이 바로 반영됩니다.

결과물인 dist 폴더에는 브라우저가 직접 읽는 HTML, CSS, Javascript와 이미지만 들어 있습니다. 이 사이트의 다른 문서들처럼 정적 파일일 뿐이므로, 서버에는 Node.js도 Vite도 필요 없습니다. 올리는 방법은 다음 문서에서 다룹니다.

첨부 · 참조 — 코드 분할 (Code Splitting)

모든 화면의 코드를 파일 하나에 담으면, 첫 화면만 보려는 방문자도 전부 내려받아야 합니다. import()를 함수처럼 쓰면(동적 import) Vite가 그 지점에서 파일을 나누고, 실행 중에 필요해질 때 내려받습니다.

Javascript
button.addEventListener('click', async () => {
  const { drawChart } = await import('./chart.js');     // 누를 때 내려받는다
  drawChart();
});
React — 화면 단위로 나누기
import { lazy, Suspense } from 'react';

const Settings = lazy(() => import('./Settings.jsx'));

function App() {
  return (
    <Suspense fallback={<p>불러오는 중…</p>}>
      <Settings />
    </Suspense>
  );
}
첨부 · 참조 — 내부에서 쓰는 도구

Vite는 여러 도구를 묶어 하나의 명령으로 쓰게 해 주는 껍데기에 가깝습니다. 오랫동안 개발 서버의 변환은 Go로 만든 esbuild가, 빌드의 묶기는 Rollup이 맡았습니다. 개발과 빌드의 도구가 달라 드물게 결과가 어긋나는 문제가 있어, 최근 버전은 Rust로 만든 Rolldown 하나로 통합하는 방향으로 바뀌고 있습니다.

사용자가 쓰는 명령과 설정은 그대로이므로, 어떤 도구가 안에서 돌아가는지는 빌드가 유난히 느리거나 플러그인 호환 문제가 생겼을 때만 신경 쓰면 됩니다. 설정의 build.rollupOptions처럼 옵션 이름에 그 흔적이 남아 있습니다.
