# Full Code Review Checklist

2026-11-10 작성

## 목적과 적용 범위

이 문서는 프로젝트 종류와 무관하게 "코드 전수 검사"를 요청받은 모든 에이전트가 따르는 공통 기준이다. 검사는 18개 항목을 빠짐없이 확인하고, 정해진 형식으로 결과를 보고한다.

- **검사 대상:** 저장소의 모든 소스 코드, 설정 파일, 스크립트, 문서
- **제외 대상:** 빌드 산출물(`dist`, `build`), 외부 벤더 코드(`node_modules`, `vendor`), 자동 생성 파일, lock 파일의 본문
- **전제:** 검사는 읽기 전용이다. 수정은 사용자가 보고서를 확인하고 요청한 뒤에만 한다.

## 검사 절차

기계가 잡을 수 있는 것은 도구로 먼저 잡고, 판단이 필요한 항목에 검토 시간을 쓴다.

1. **범위 확정:** 저장소 구조를 파악하고 제외 대상을 걸러 낸다.
2. **명세 확보:** 요구사항·명세 문서를 찾는다. 없으면 사용자에게 요청하고, 받지 못하면 18번 항목을 "검사 불가"로 보고한다.
3. **자동 도구 실행:** 린트, 타입 체크, 중복·미사용 코드, 순환 참조, 시크릿, 취약점 도구를 돌린다.
4. **항목별 수동 검토:** 18개 항목을 순서대로 확인한다. 파일을 일부만 보고 추정하지 않는다.
5. **결과 정리:** 지적 사항을 보고 형식에 맞춰 심각도 순으로 정렬한다.
6. **검증:** Critical·High 지적은 해당 코드를 다시 열어 사실인지 확인한 뒤 보고한다.

## 체크리스트

18개 항목을 모두 확인한다. 문제가 없는 항목도 "이상 없음"으로 보고해 누락과 구분한다.

| # | 영역 | 항목 | 점검 내용 |
| --- | --- | --- | --- |
| 1 | 구조 | 파일 크기·복잡도 | 비대해진 파일·함수, 너무 많은 책임을 가진 파일, 과도한 중첩과 분기 |
| 2 | 구조 | 응집도 | 각 모듈·컴포넌트가 단일 책임에 집중하는지, 파편화된 로직이나 혼재된 관심사가 없는지 |
| 3 | 구조 | 결합도 | 모듈 간 강한 결합, 변경 시 연쇄 부작용, 순환 참조 |
| 4 | 구조 | 중복·죽은 코드 | 복사·붙여넣기 중복 블록, 미사용 import·함수·파일, 주석 처리된 채 방치된 코드 |
| 5 | 구조 | 명명 규칙 | 변수·함수·컴포넌트·모듈 이름이 의도와 역할을 명확하고 일관되게 드러내는지 |
| 6 | 안전성 | 하드코딩 | 시크릿, 엔드포인트, 매직 넘버가 설정 파일이나 `.env`로 분리되었는지. `.env`가 `.gitignore`에 있는지, git 이력에 커밋된 시크릿이 없는지 |
| 7 | 안전성 | 보안 | 입력값 검증, 인젝션(SQL·XSS·커맨드), 인증·인가 누락, 파일 경로 조작, 로그에 남는 민감정보 |
| 8 | 안전성 | 의존성 관리 | 미사용·중복 패키지, 알려진 취약점(CVE), lock 파일로 버전 고정, 라이선스 호환성 |
| 9 | 안전성 | 데이터·개인정보 | 개인정보가 담긴 데이터(녹음, 연락처 등)의 저장 위치, 보존 기간, 접근 권한 |
| 10 | 견고성 | 예외·에러 처리 | 빈 `catch` 블록, 조용한 실패, 외부 호출(API·DB)의 타임아웃·재시도, 사용자에게 보이는 에러 메시지 |
| 11 | 견고성 | 타입 안정성·정적 분석 | 타입 체크 통과 여부, `any`나 타입 무시 주석의 남용, 방치된 린트 경고 |
| 12 | 견고성 | 테스트 | 핵심 로직의 테스트 유무와 커버리지, 엣지 케이스 누락, 깨지거나 불안정한 테스트 |
| 13 | 견고성 | 로깅·관측성 | 장애 원인을 추적할 만큼 로그가 남는지, 로그 레벨이 일관적인지, 과도한 로그가 없는지 |
| 14 | 성능 | 성능 병목 | N+1 쿼리, 메모리 누수(리스너·타이머 미해제), 불필요한 반복, 비효율적인 비동기 처리나 리렌더링 |
| 15 | 성능 | 동시성·자원 관리 | 메인·UI 스레드나 이벤트 루프를 막는 무거운 작업, 경쟁 상태, 파일·DB 연결·서브프로세스 미해제 |
| 16 | 문서·명세 | LLM 인덱싱 친화성 | 파일 상단 헤더(YAML frontmatter, JSDoc, Docstring)의 구조화, `AGENTS.md`·`CLAUDE.md` 유무, 주석이 코드와 어긋나지 않는지 |
| 17 | 문서·명세 | 문서 정합성 | README, 설치·실행 방법, `.env.example`이 실제 코드와 맞는지 |
| 18 | 문서·명세 | 명세 정합성 | 요구사항별로 구현 위치, 미구현, 부분 구현을 표로 대조. 명세 문서가 있어야 검사 가능 |

## 판정 기준과 도구

아래 수치를 넘으면 지적 대상이다. 프로젝트에 자체 기준이 있으면 그쪽을 따른다.

| 대상 | 기준 |
| --- | --- |
| 파일 길이 | 500줄 초과 |
| 함수 길이 | 50줄 초과 |
| 순환 복잡도 | 10 초과 |
| 중첩 깊이 | 4단계 초과 |
| 함수 매개변수 | 5개 초과 |
| 중복 블록 | 같은 코드 10줄 이상이 2곳 이상 |

자동 도구는 프로젝트 언어에 맞는 것을 고른다. 설치되어 있지 않으면 설치 여부를 사용자에게 묻고, 쓸 수 없으면 수동으로 검토한 뒤 그 사실을 보고서에 적는다.

| 용도 | JavaScript/TypeScript | Python |
| --- | --- | --- |
| 린트·타입 | eslint, tsc | ruff, mypy |
| 중복 코드 | jscpd | jscpd |
| 미사용 코드 | knip | vulture |
| 순환 참조 | madge | pydeps |
| 시크릿 | gitleaks | gitleaks |
| 취약점 | npm audit | pip-audit |

## 결과 보고 형식

보고서는 요약, 지적 목록, 항목별 현황의 세 부분으로 구성한다.

1. **요약:** 심각도별 지적 건수와 가장 먼저 고쳐야 할 3건
2. **지적 목록:** 심각도 순으로 정렬하고, 각 지적에 아래 네 가지를 적는다.
   - 심각도와 항목 번호
   - 위치: `파일 경로:줄 번호`
   - 근거: 무엇이 왜 문제인지
   - 수정안: 구체적인 변경 방법
3. **항목별 현황:** 18개 항목 각각의 지적 건수 또는 "이상 없음", "검사 불가(사유)"

| 심각도 | 기준 | 예 |
| --- | --- | --- |
| Critical | 보안 사고, 데이터 손실, 서비스 중단으로 이어짐 | 커밋된 API 키, SQL 인젝션 |
| High | 기능 오동작이나 뚜렷한 성능 저하를 일으킴 | 메인 스레드 차단, 조용한 실패, 명세 미구현 |
| Medium | 유지보수를 어렵게 함 | 900줄 파일, 순환 참조, 중복 코드 |
| Low | 개선하면 좋은 수준 | 모호한 이름, 미사용 import |

## 에이전트 공유 방법

에이전트마다 지침을 읽는 경로가 다르므로 세 경로를 함께 쓴다. 이 문서가 원본이고, 나머지 둘은 이 문서의 사본이다.

| 경로 | 닿는 대상 | 설정 방법 |
| --- | --- | --- |
| Claude 스킬 `code-full-audit` | 내 계정의 모든 Claude 세션 | 대화에 뜬 스킬 카드에서 저장. 이후 "코드 전수 검사해줘"라고 하면 자동 적용 |
| 저장소의 `docs/CODE_AUDIT.md` | 그 저장소에서 일하는 모든 에이전트(Claude Code, Codex, Cursor 등) | 파일을 저장소에 넣고 `AGENTS.md`와 `CLAUDE.md`에 참조 한 줄 추가 |
| 이 문서 링크 | 팀원과 링크를 받은 Claude 세션 | 문서의 공유 기능으로 링크 전달 |

`AGENTS.md`와 `CLAUDE.md`에 넣을 참조 문구:

```markdown
## 코드 전수 검사
"전수 검사", "전수 조사", "full audit" 요청을 받으면 docs/CODE_AUDIT.md를 먼저 읽고,
그 문서의 절차·18개 항목·보고 형식을 그대로 따른다.
```

기준을 바꿀 때는 이 문서를 먼저 고치고, 스킬과 저장소 파일에 같은 변경을 반영한다.
